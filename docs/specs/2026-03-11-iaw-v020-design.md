# IAW v0.2.0 Design Specification

**Date:** 2026-03-11
**Status:** Draft
**Scope:** InteractiveAgents opensource project (E:\IAW\InteractiveAgents)

---

## Overview

v0.2.0 transforms IAW from a basic agent framework into a fully orchestrated, memory-aware, multi-model runtime. The release introduces code-generated orchestration with typed agent interfaces, LLM models as first-class agents, persistent semantic memory with provenance tracking, durable task recovery, and a complete communication model.

## Design Principles

- **Interfaces are the single source of truth** — no attributes for discovery, no untyped events
- **Every agent is an Orleans grain** — LLMs, memories, orchestrators all follow the same Agent base pattern
- **Three communication channels** — task streams, typed pub/sub, P2P. No overlap, no YAGNI.
- **Automatic intelligence** — memory injection happens before every LLM call without agents asking
- **Opt-in durability** — in-memory by default for quick dev, CosmosDB for production persistence

## Agent Base Class Changes

v0.2.0 simplifies the Agent constructor. The v0.1.0 constructor requires 5 parameters:

```csharp
// v0.1.0
Agent(state, eventLog, chatClient, history, trackingItems)
```

v0.2.0 internalizes `history` and `trackingItems` — they are implementation details that derived agents should not need to pass through:

```csharp
// v0.2.0
Agent(state, eventLog, chatClient)
```

The Agent base class still uses durable history and tracking internally, but manages their `[Memory]` injection itself. This is a **breaking change** for any custom agents that pass all 5 parameters (see Section 12).

## Type Constraints

P2P messages and stream events have different base interfaces:
- `IReceiver<TMessage>` constrains `TMessage : IAgentMessage` — directed messages
- `IStreamProducer<TEvent>` / `IStreamConsumer<TEvent>` constrains `TEvent : IEvent` — pub/sub events
- Task stream events also implement `IEvent`

These are distinct type hierarchies. `TaskAssignedMessage : IAgentMessage` goes through P2P. `TestsPassedEvent : IEvent` goes through streams. Do not mix them.

## Grain ID Convention

InterfaceCatalog converts interface names to grain IDs using this algorithm:
1. Strip leading `I` prefix: `IRoslyn` -> `Roslyn`
2. Insert hyphens before uppercase letters (kebab-case): `FileSystem` -> `file-system`
3. Lowercase everything

Examples:
| Interface | Grain ID |
|-----------|----------|
| `IRoslyn` | `roslyn` |
| `IFileSystem` | `file-system` |
| `IPersonalAssistant` | `personal-assistant` |
| `IDotNet` | `dot-net` |
| `INuGet` | `nu-get` |
| `IGpt52` | `gpt52` |
| `IClaude45Haiku` | `claude45-haiku` |
| `IOpus46` | `opus46` |
| `ICodeOrchestrator` | `code-orchestrator` |

Note: numeric sequences are NOT split. `Gpt52` stays `gpt52`, not `gpt-52`. `Opus46` stays `opus46`.

## 1. InterfaceCatalog — Interface-Only Discovery

### What

Reflection engine that discovers all `IAgent`-derived interfaces at runtime and builds a typed catalog of the entire agent API surface.

### How It Works

1. Scans `AppDomain` for all `Agent` subclasses
2. Finds matching `IXxxAgent` interface per class
3. Extracts method signatures (name, params, return type)
4. Detects `IStreamProducer<T>`, `IStreamConsumer<T>`, `IReceiver<T>` from implemented interfaces
5. Converts interface to grain ID: `IRoslyn` -> `"roslyn"`, `IFileSystem` -> `"file-system"`
6. `ToPromptString()` serializes the full API surface for LLM consumption

### Key Types

```csharp
public record CatalogEntry(
    string InterfaceName,
    string FullTypeName,
    string DefaultGrainId,
    IReadOnlyList<MethodSignature> Methods,
    IReadOnlyList<string> Produces,
    IReadOnlyList<string> Consumes);

public record MethodSignature(
    string Name,
    IReadOnlyList<ParameterInfo> Parameters,
    string ReturnType);
```

### Integration

- `AgentRegistrationStartupTask` uses `InterfaceCatalog` for subscriber pre-activation (replacing attribute scanning)
- `CodeOrchestrator` uses `ToPromptString()` to build LLM system prompts
- MCP tools use it for `agent_list_all`

### Exclusion List

Base interfaces excluded from catalog: `IAgent`, `IDynamicAgent`, `IConversationalAgent`, `IEventDrivenAgent`, `ITrackableAgent`, `IStreamingAgent`, `IObservableAgent`, `IStatefulAgent`

### Files

- `src/Core/Orchestration/InterfaceCatalog.cs`
- `test/Core.Tests/Orchestration/InterfaceCatalogTests.cs`

## 2. Communication Model — Three Channels

### Breaking Changes from v0.1.0

**Removed:**
- `PublishAsync(string eventName, Dictionary<string, object> payload)` — untyped, replaced by typed `PublishToStream<T>()`
- `HandleEvent(AgentEvent)` on `IAgent` — untyped catch-all, replaced by `IStreamConsumer<T>`
- `AgentEvent` as a public API for constructing events — internal only for event log storage

**Dispatch mechanism change:** In v0.1.0, `Agent.Streams.cs` routes ALL stream events through the untyped `HandleEvent(AgentEvent)`. In v0.2.0, the stream subscription wiring in `SubscribeToStreamConsumerInterfaces()` directly invokes the typed `OnStreamEventAsync(TEvent, StreamSequenceToken?)` method on the concrete `IStreamConsumer<TEvent>` implementation. The untyped dispatch path is removed entirely.

**New method on Agent base:**
```csharp
// Publish typed event to task stream (replaces PublishToStream(AgentEvent))
protected Task PublishToTaskStream<TEvent>(string taskId, TEvent evt) where TEvent : IEvent;

// Publish typed event to reactive pub/sub (existing IStreamProducer<T> pattern)
protected Task PublishToStream<TEvent>(TEvent evt) where TEvent : IEvent;
```

### Task Stream Event Types

### Task Stream Lifecycle

- **Creation**: Orchestrator publishes the first event to `task/{taskId}` — the stream is created implicitly by Orleans.
- **Completion**: Orchestrator publishes `TaskCompletedEvent` as a terminal marker. Subscribers can use this to unsubscribe.
- **Cleanup**: Orleans streams are virtual and never explicitly destroyed. Old task streams are simply abandoned. Memory agents retain the relevant knowledge; the stream itself can be garbage collected by the storage provider.

### Channel 1: Task Streams

**Stream ID:** `task/{taskId}`

All agents working on a task push to the same stream. The orchestrator and any participating agent can read it to understand context.

**Use cases:**
- **Orchestrator recovery**: Silo restarts, reads task stream, sees completed/in-progress steps, resumes
- **Agent context awareness**: Agent reads task stream to see what other agents have done
- **Consilium aggregation**: Multiple LLM responses land on task stream, consilium logic aggregates
- **Progress tracking**: DevUI subscribes to task stream for real-time progress
- **Post-mortem**: Full execution history for debugging

### Channel 2: Typed Pub/Sub

**Interfaces:** `IStreamProducer<TEvent>` / `IStreamConsumer<TEvent>`

Fire-and-forget, many-to-many. Producer doesn't know or care who's listening.

**Use cases:**
- **CI/CD pipeline**: `TestsPassedEvent` -> Deployer triggers deployment. Add consumers without touching producers.
- **Knowledge accumulation**: `CodeChangedEvent` -> CodeMemory re-indexes
- **Self-improvement triggers**: `ReviewCompletedEvent` -> PatternMemory extracts patterns
- **Notification fan-out**: `UserNotificationEvent` -> Notification agent routes to channels

### Channel 3: P2P (IReceiver\<T\>)

Agent-to-agent, one-to-one, with accept/reject semantics.

**Use cases:**
- **Task delegation**: PersonalAssistant sends `TaskAssignedMessage` -> agent accepts/rejects
- **Code review request**: DotNet sends `ReviewRequestMessage` -> Reviewer reviews, sends `ReviewCompletedMessage`
- **Build artifacts handoff**: Roslyn sends `CompilationResultMessage` -> DotNet builds
- **Failure escalation**: Any agent sends `TaskFailedMessage` -> PersonalAssistant decides

### Auto-Logging Rule

Every interaction across all three channels is automatically logged to the agent's event log:

| Action | Auto-logged as |
|--------|---------------|
| `PublishToStream(evt)` on task stream | `EventLogEntry(Produced, taskId, eventType, timestamp)` |
| `IReceiver.Receive(msg)` accepted | `EventLogEntry(Received, senderId, messageType, timestamp)` |
| `IStreamConsumer.OnStreamEvent(evt)` fired | `EventLogEntry(Consumed, streamId, eventType, timestamp)` |
| `GetResponse(prompt)` completed | `EventLogEntry(LlmCall, model, tokenUsage, timestamp)` |

### Combined Flow Example

```
User: "Fix the failing test in AuthService"

1. PersonalAssistant creates task-abc123 stream
2. PA sends TaskAssignedMessage to Roslyn via IReceiver          <- P2P
3. Roslyn analyzes, pushes results to task/task-abc123            <- Task Stream
4. Roslyn sends CompilationResultMessage to DotNet via IReceiver  <- P2P
5. DotNet reads task stream for context                           <- Task Stream
6. DotNet fixes code, runs tests, pushes progress                 <- Task Stream
7. DotNet produces TestsPassedEvent                               <- Typed Pub/Sub
8. Deployer wakes up (consumes TestsPassedEvent)                  <- Typed Pub/Sub
9. Reviewer wakes up too, does quality check                      <- Typed Pub/Sub
10. Both push results to task/task-abc123                         <- Task Stream
11. Orchestrator reads task stream, sees all done, closes task
```

### Agent Hierarchy

```
Agent (base)
  └── LLM (abstract)

        ├── Gpt52         : LLM, IGpt52
        ├── Gpt53         : LLM, IGpt53

        ├── Gpt4oMini     : LLM, IGpt4oMini
        ├── Gemini31      : LLM, IGemini31

        ├── Qwen25        : LLM, IQwen25
        └── Llama32       : LLM, ILlama32
```

### What LLM Adds

`LLM` is an abstract class extending `Agent`. Each subclass represents a frontier model as a grain.

- Uses `[Llm<TSelf>]` — each LLM agent talks to its own model
- Inherits everything from Agent: state, streams, events, tools, reminders, memory
- Can have tools if needed, but doesn't by default
- SystemPrompt defaults to: "You are {DisplayName}. Answer directly and accurately."
- Tracks per-model token usage, latency in grain state
- `InterfaceCatalog` discovers `IOpus46`, `IGpt52` etc. for typed orchestration

### Concurrency: LLM Grain Pooling

Orleans grains are single-activation and single-threaded. If two concurrent orchestrations both call `client.GetGrain<IOpus46>("opus46")`, the second request queues behind the first. For consilium and MapReduce scenarios, callers should use **unique grain IDs per invocation** to enable parallelism:

```csharp
// Parallel: each call gets its own grain activation
var opus1 = client.GetGrain<IOpus46>($"opus46-{Guid.NewGuid():N}"[..20]);
var opus2 = client.GetGrain<IOpus46>($"opus46-{Guid.NewGuid():N}"[..20]);
var results = await Task.WhenAll(opus1.GetResponse(prompt1), opus2.GetResponse(prompt2));
```

The `InterfaceCatalog.DefaultGrainId` is the canonical single-instance ID. Generated orchestration scripts use unique IDs for parallel calls. LLM agents are stateless by default so multiple activations are safe.

### No Special Methods

`LLM` does NOT add `Ask()` or any new methods. `GetResponse()` and `GetResponseStream()` from the Agent base class are sufficient. LLM agents are just agents whose purpose is to be a model endpoint.

## 4. Code Orchestration

### OrchestrationCompiler

Roslyn-based safety net. Before any generated script executes, it must compile against actual agent interface assemblies.

**Flow:**
```
LLM generates C# script
  -> OrchestrationCompiler.Compile(source)
  -> Roslyn CSharpCompilation with agent interface references
  -> Success? -> ScriptExecutor runs it
  -> Errors? -> Feed errors back to LLM, retry (up to 3 attempts)
```

### Typed Script Generation

v0.1.0 scripts use generic `IAgent`. v0.2.0 uses typed interfaces from InterfaceCatalog:

```csharp
// v0.1.0 (generic)
var agent = client.GetGrain<IAgent>("roslyn");

// v0.2.0 (typed)
var roslyn = client.GetGrain<IRoslyn>("roslyn");
var dotnet = client.GetGrain<IDotNet>("dot-net");
var github = client.GetGrain<IGitHub>("git-hub");
var opus = client.GetGrain<IOpus46>("opus-46");
```

### CodeOrchestrator

**`CodeOrchestrator : Agent, ICodeOrchestrator`**

Durable orchestration using standard `IDurableDictionary` and `IDurableList`.

```csharp
public class CodeOrchestrator(
    [Memory("agent-state")] IDurableDictionary<string, StateEntry> state,
    [Memory("agent-events")] IDurableList<AgentEvent> eventLog,
    [Memory("orchestration-steps")] IDurableList<StepRecord> steps,
    [Memory("orchestration-results")] IDurableDictionary<string, StepResult> results,
    [Llm<Opus46>] IChatClient chatClient)
    : Agent(state, eventLog, chatClient), ICodeOrchestrator
```

Note: `[Memory]` stores are per-grain-instance in Orleans 10. Two orchestrator grains with different IDs each get isolated `orchestration-steps` and `orchestration-results` collections.

**`ICodeOrchestrator` interface:**

```csharp
public interface ICodeOrchestrator : IAgent
{
    Task<string> CreateTask(string description, CancellationToken ct = default);
    Task<OrchestrationState> GetTaskState(string taskId, CancellationToken ct = default);
    Task ResumeTask(string taskId, CancellationToken ct = default);
    Task CancelTask(string taskId, CancellationToken ct = default);
}
```

**Key types:**

```csharp
[GenerateSerializer]
public record StepRecord(
    [property: Id(0)] int StepIndex,
    [property: Id(1)] string AgentId,
    [property: Id(2)] string Action,
    [property: Id(3)] StepStatus Status,
    [property: Id(4)] Dictionary<string, string> Parameters);

[GenerateSerializer]
public record StepResult(
    [property: Id(0)] string Output,
    [property: Id(1)] TimeSpan Duration,
    [property: Id(2)] string AgentId,
    [property: Id(3)] DateTimeOffset CompletedAt);

public enum StepStatus { Pending, Running, Completed, Failed, Retrying, Escalated }

public enum OrchestrationStatus { Created, Running, Paused, Failed, Completed }
```

**State model — all durable:**

```
IDurableList<StepRecord> steps:
  [0] { StepIndex: 0, AgentId: "roslyn", Action: "analyze", Status: Completed }
  [1] { StepIndex: 1, AgentId: "dot-net", Action: "build", Status: Completed }
  [2] { StepIndex: 2, AgentId: "reviewer", Action: "review", Status: Running }
  [3] { StepIndex: 3, AgentId: "git-hub", Action: "create-pr", Status: Pending }

IDurableDictionary<string, StepResult> results:
  "step-0" -> { Output: "...", Duration: 12s, AgentId: "roslyn" }
  "step-1" -> { Output: "...", Duration: 45s, AgentId: "dot-net" }

IDurableDictionary<string, StateEntry> state:
  "task-id"       -> "task-abc123"
  "status"        -> "Running"
  "current-step"  -> "2"
  "retry-count-2" -> "1"
```

**Step lifecycle:**
```
Pending -> Running -> Completed
                   -> Failed -> Retrying -> Running (up to 3 retries)
                                          -> Escalated (notify supervisor)
```

**Recovery flow:**
1. Silo crashes mid-task, step 2 was running
2. Silo restarts, Orleans reactivates CodeOrchestrator grain
3. `IDurableDictionary`/`IDurableList` auto-load from storage
4. State already there: steps 0-1 completed, step 2 running
5. Orchestrator marks step 2 as Retry, increments retry count
6. Re-generates script for step 2, executes
7. On success: updates step 2 status, moves to step 3

### Code Orchestration Scenarios

#### Scenario 1: Consilium — Multi-Model Code Review

```csharp
var opus = client.GetGrain<IOpus46>("opus-46");
var sonnet = client.GetGrain<ISonnet46>("sonnet-46");
var gpt = client.GetGrain<IGpt52>("gpt-52");

var reviews = await Task.WhenAll(
    opus.GetResponse($"Review this code:\n{code}"),
    sonnet.GetResponse($"Review this code:\n{code}"),
    gpt.GetResponse($"Review this code:\n{code}"));

var allIssues = reviews.SelectMany(r => ParseIssues(r));
var confirmedIssues = allIssues
    .GroupBy(i => i.Location)
    .Where(g => g.Count() >= 2)
    .Select(g => g.OrderByDescending(i => i.Severity).First());
```

#### Scenario 2: Adaptive Routing — Cheap First, Escalate

```csharp
var haiku = client.GetGrain<IClaude45Haiku>("claude-45-haiku");
var response = await haiku.GetResponse(prompt);

if (response.Contains("I'm not sure") || response.Length < 50)
{
    var opus = client.GetGrain<IOpus46>("opus-46");
    response = await opus.GetResponse(
        $"Previous attempt was uncertain:\n{response}\n\nOriginal task:\n{prompt}");
}
```

#### Scenario 3: Parallel Agent Pipeline

```csharp
var roslyn = client.GetGrain<IRoslyn>("roslyn");
var dotnet = client.GetGrain<IDotNet>("dot-net");
var reviewer = client.GetGrain<IReviewer>("reviewer");
var github = client.GetGrain<IGitHub>("git-hub");

var analysis = await roslyn.GetResponse("Analyze src/Core/Agent.cs");
var syntaxErrors = JsonSerializer.Deserialize<List<SyntaxError>>(analysis);

if (syntaxErrors.Any(e => e.Severity == "Error"))
{
    foreach (var error in syntaxErrors.Where(e => e.Severity == "Error"))
        await dotnet.GetResponse($"Fix error at {error.File}:{error.Line}: {error.Message}");
}

var buildResult = await dotnet.GetResponse("dotnet build");
if (buildResult.Contains("Build succeeded"))
{
    var review = await reviewer.GetResponse("Review the changes");
    if (!review.Contains("BLOCKED"))
        await github.GetResponse("Create PR with title 'Fix syntax errors'");
}
```

#### Scenario 4: Fan-Out Search with Deduplication

```csharp
var knowledge = client.GetGrain<IKnowledge>("knowledge");
var sonnet = client.GetGrain<ISonnet46>("sonnet-46");
var gpt = client.GetGrain<IGpt52>("gpt-52");

var results = await Task.WhenAll(
    knowledge.GetResponse("Find all files related to authentication"),
    sonnet.GetResponse("What files would typically handle auth in a .NET project?"),
    gpt.GetResponse("List common authentication patterns in ASP.NET Core"));

var files = results
    .SelectMany(r => Regex.Matches(r, @"[\w/]+\.cs").Select(m => m.Value))
    .GroupBy(f => f)
    .OrderByDescending(g => g.Count())
    .Select(g => g.Key)
    .ToList();
```

#### Scenario 5: Multi-Model Code Generation with Compilation Validation

```csharp
var roslyn = client.GetGrain<IRoslyn>("roslyn");
var opus = client.GetGrain<IOpus46>("opus-46");
var sonnet = client.GetGrain<ISonnet46>("sonnet-46");
var gpt = client.GetGrain<IGpt52>("gpt-52");

var implementations = await Task.WhenAll(
    opus.GetResponse("Implement IUserRepository with EF Core"),
    sonnet.GetResponse("Implement IUserRepository with EF Core"),
    gpt.GetResponse("Implement IUserRepository with EF Core"));

var results = new List<(int Index, string Code, bool Compiles)>();
for (int i = 0; i < implementations.Length; i++)
{
    var validation = await roslyn.GetResponse($"Validate this compiles:\n{implementations[i]}");
    results.Add((i, implementations[i], !validation.Contains("error")));
}

var winner = results.FirstOrDefault(r => r.Compiles);
if (winner == default)
{
    var errorReport = string.Join("\n", results.Select(r => $"Attempt {r.Index} failed"));
    await opus.GetResponse($"All three failed:\n{errorReport}\nMerge best parts and fix.");
}
```

#### Scenario 6: Self-Healing Pipeline with Retry and Fallback Models

```csharp
var dotnet = client.GetGrain<IDotNet>("dot-net");

for (int attempt = 0; attempt < 3; attempt++)
{
    var build = await dotnet.GetResponse("dotnet build");
    if (build.Contains("Build succeeded")) break;

    IAgent fixer = attempt switch
    {
        0 => client.GetGrain<IClaude45Haiku>("claude-45-haiku"),
        1 => client.GetGrain<ISonnet46>("sonnet-46"),
        _ => client.GetGrain<IOpus46>("opus-46"),
    };

    await fixer.GetResponse($"Build failed (attempt {attempt + 1}):\n{build}\nFix the errors.");
}
```

#### Scenario 7: MapReduce over Codebase

```csharp
var fs = client.GetGrain<IFileSystem>("file-system");
var filesJson = await fs.GetResponse("List all .cs files in src/");
var files = JsonSerializer.Deserialize<List<string>>(filesJson);

var analyses = new ConcurrentBag<(string File, string Analysis)>();
foreach (var batch in files.Chunk(5))
{
    var tasks = batch.Select(async file =>
    {
        // unique grain ID per call enables true parallelism
        var sonnet = client.GetGrain<ISonnet46>($"sonnet46-{Guid.NewGuid():N}"[..20]);
        var result = await sonnet.GetResponse($"Analyze {file} for security vulnerabilities");
        analyses.Add((file, result));
    });
    await Task.WhenAll(tasks);
}

var allFindings = string.Join("\n---\n",
    analyses.Select(a => $"{a.File}:\n{a.Analysis}"));
var summary = await client.GetGrain<IOpus46>("opus-46")
    .GetResponse($"Synthesize into a prioritized security report:\n{allFindings}");
```

### The Power of Code Orchestration

| Capability | JSON plans can't | C# orchestration can |
|-----------|-----------------|---------------------|
| Conditional logic | Static step list | `if/else`, `switch`, pattern matching |
| Loops/retry | Fixed count | `for`, `while`, `foreach` with break |
| Parallel execution | Sequential or all | `Task.WhenAll`, batching |
| Data transformation | Pass raw strings | LINQ, regex, JSON, typed models |
| Error handling | Fail or skip | `try/catch`, fallback models |
| Aggregation | None | `GroupBy`, scoring, voting |
| State machines | External | `enum` + `switch`, complex flow |

### Agent Hierarchy

```

  └── Memory (abstract)
        ├── UserMemory      : Memory, IUserMemory
        ├── ProjectMemory   : Memory, IProjectMemory
        ├── PatternMemory   : Memory, IPatternMemory
```

### Memory Base Class

```csharp
public abstract class Memory(
    [Memory("agent-state")] IDurableDictionary<string, StateEntry> state,
    [Memory("agent-events")] IDurableList<AgentEvent> eventLog,
    [Memory("memories")] IDurableList<MemoryEntry> memories,
    [Llm<Claude45Haiku>] IChatClient chatClient,
    IEmbeddingGenerator<string, Embedding<float>> embedder,
    IVectorStore vectorStore)

```

**Vector store abstraction:** The Memory base uses `IVectorStore` (from `Microsoft.Extensions.VectorData`) instead of `QdrantClient` directly. This enables:
- **Dev mode (no Docker):** `InMemoryVectorStore` — memories work but don't persist across restarts. Enabled by default when no Qdrant is configured.
- **Production:** `QdrantVectorStore` — persistent vector search via Qdrant container.

The `ElBruno.LocalEmbeddings.VectorData` package provides `InMemoryVectorStore` DI helpers that work with `IEmbeddingGenerator`.

**Error handling for LLM failures in memory agents:** If the LLM is unavailable (rate limit, network), `Observe()` stores the raw content with embedding but skips LLM-based extraction. A durable job retries extraction on the next consolidation cycle. Memory agents never throw on LLM failure — they degrade gracefully.

### Core Capabilities

| Method | Purpose |
|--------|---------|
| `Observe(content, provenance)` | Embed content, store in Qdrant + durable list |
| `Search(query, topK, minScore)` | Vector similarity search against own collection |
| `Consolidate()` | Merge similar memories, generalize patterns |
| `Decay()` | Reduce relevance scores over time, prune low-value |
| `Forget(memoryId)` | Explicit removal |

### Trust Hierarchy

```
user-input         -> highest trust (1.0) — user explicitly said this
user-correction    -> highest trust (1.0) — user corrected a mistake
conversation       -> high trust (0.9)    — direct interaction
task-stream        -> medium trust (0.7)  — observed behavior
pattern-inference  -> lower trust (0.6)   — derived by LLM reasoning
```

### Qdrant Collections

Each memory agent has its own Qdrant collection for namespace isolation:
- `iaw-user-memory`
- `iaw-project-memory`
- `iaw-pattern-memory`
- `iaw-episode-memory`
- `iaw-code-memory`

### Memory Agent Specializations

**UserMemory** — Preferences, personal facts, corrections
- Observes conversation streams
- LLM extracts personal facts: "birthday is March 10", "hates XML comments"
- User corrections get TrustScore=1.0, supersede old memories
- Durable job: birthday/anniversary reminders

**ProjectMemory** — Technical facts about the codebase
- Observes task streams where FileSystem/Git/DotNet act
- Extracts: "project uses Orleans 10", "auth is JWT"
- Detects when facts change, marks old facts as superseded

**PatternMemory** — Recurring solutions and anti-patterns
- Observes `ReviewCompletedEvent`, `TaskCompletedEvent`, `TaskFailedEvent`
- Identifies patterns across multiple episodes
- Promoted from EpisodeMemory when pattern appears 3+ times

**EpisodeMemory** — What happened on specific tasks
- Observes all task streams
- Stores task summaries with rich provenance
- Source for PatternMemory promotion

**CodeMemory** — Semantic code index
- Observes `CodeChangedEvent` from FileSystem/Git
- Embeds code snippets, file summaries, API signatures
- Enables semantic code search beyond grep

### Embedding Infrastructure — Pluggable

All implement `IEmbeddingGenerator<string, Embedding<float>>` from Microsoft.Extensions.AI:

```csharp
var iaw = builder.AddIAW()
    .WithLocalEmbeddings()                           // ElBruno.LocalEmbeddings (ONNX, default)
    // OR
    .WithOllamaEmbeddings("nomic-embed-text")        // via Ollama
    // OR
    .WithOpenAIEmbeddings("text-embedding-3-small")  // cloud
```

### Consolidation via Durable Jobs

```
Every 6 hours (configurable):
  Phase 1 — Decay (runs first):
    1. All memory agents run Decay()
    2. Memories not accessed in 30 days: relevance *= 0.8
    3. Below threshold (0.1): archived or pruned

  Phase 2 — Consolidation (runs after decay):
    1. PatternMemory scans EpisodeMemory for similar entries
    2. LLM groups and generalizes
    3. Stores generalized pattern with relevance=1.0, links back to source episodes
    4. Newly created patterns are NOT decayed in the same cycle
```

Ordering matters: decay first removes stale entries, then consolidation creates fresh patterns from surviving episodes. New patterns start with full relevance.

### Concrete Scenarios

**1. User Preference Learning:**
User says "Stop adding summary XML comments" -> UserMemory observes on task stream -> LLM extracts: "code-style preference: no XML summary comments" -> Stored with embedding -> Next time ANY agent generates code, auto-injection includes the preference.

**2. Failure Pattern Recognition:**
Task-001: build fails, fix works. Task-007: same pattern. Task-015: same again. -> EpisodeMemory has 3 instances -> Consolidation promotes to PatternMemory as generalized rule -> Next occurrence, auto-injected.

**3. Birthday Reminder:**
User says "My birthday is March 10th" -> UserMemory stores -> Registers durable job: remind on March 9th -> Reminder fires -> Sends NotificationRequest to INotification.

**4. Cross-Task Knowledge Transfer:**
Task-042 solves CosmosDB indexing issue -> EpisodeMemory stores, CodeMemory indexes solution -> Task-089 has similar DB issue -> Auto-injection surfaces the previous solution -> Solved on first try.

**5. Code Review Memory:**
Reviewer finishes PR #47 -> PatternMemory consumes ReviewCompletedEvent -> Extracts: "null-check gaps in repository layer" -> Over time builds profile -> Next review auto-injects: "Pay attention to null checks in repositories."

## 6. AIContextProvider Integration

### Existing Pattern

`IAIContextProvider` interface with two hooks:
- `ProvideContextAsync` — called BEFORE every LLM call, injects additional messages
- `StoreContextAsync` — called AFTER every LLM response, persists data

### New Context Providers

#### MemoryContextProvider

```
ProvideContextAsync:
  1. Query all memory agents in parallel
  2. Rank results by relevance x trust score
  3. Top 5 memories injected as system context
  4. Agent never explicitly asks -- it just knows

StoreContextAsync:
  1. Send (prompt, response) pair to relevant memory agents
  2. Memory agents decide what to extract and store
  3. Includes provenance metadata
```

#### TaskStreamContextProvider

```
ProvideContextAsync:
  1. Read recent events from current task stream
  2. Format as context: "Here's what happened on this task so far..."
  3. Agent automatically knows what other agents have done

StoreContextAsync:
  1. Push agent's response as event to task stream
  2. Other agents and supervisor can see it
```

#### Agent Base Class Integration

```csharp
protected override IReadOnlyList<IAIContextProvider> GetContextProviders() =>
[
    new MemoryContextProvider(memoryAgents),
    new TaskStreamContextProvider(currentTaskId),
    // agents can add custom providers
];
```

## 7. TaskSupervisor

**`TaskSupervisor : Agent, ITaskSupervisor`**

Watches task streams, detects stalls, drift, deadlocks. Escalates when needed.

### How It Works

- Subscribes to task streams via `IStreamConsumer<TaskStreamEvent>`
- Durable jobs scan active tasks every 2 minutes
- Stores active task registry in `IDurableDictionary<string, TaskHealthRecord>`
- Has its own LLM to reason about progress
- Sends `IReceiver<SupervisorMessage>` to stuck agents
- Publishes `TaskHealthEvent` to task stream for DevUI

### TaskHealthRecord

```csharp
[GenerateSerializer]
public record TaskHealthRecord(
    [property: Id(0)] string TaskId,
    [property: Id(1)] string CurrentAgentId,
    [property: Id(2)] DateTimeOffset LastEventAt,
    [property: Id(3)] int StepIndex,
    [property: Id(4)] TaskHealthStatus Health,
    [property: Id(5)] int StallCount);

public enum TaskHealthStatus
{
    Healthy,
    Slow,
    Stalled,
    Drifted,
    Deadlocked
}
```

### What It Watches

| Signal | Reaction |
|--------|----------|
| No events for N minutes | Ping assigned agent: "Are you stuck?" |
| Agent reports error | Decide: retry, reassign, escalate |
| Agent deviates from plan | Compare events against plan, flag drift |
| Task running too long | Timeout warning, escalation |
| Multiple agents idle on same task | Detect deadlock |

## 9. Notification Agent (Revised)

`Notification : Agent, INotificationAgent, IReceiver<NotificationRequest>`

**Naming:** The grain interface is renamed from `INotification` to `INotificationAgent` to avoid collision with `Core.Messages.INotification` (message marker interface). The old `IAW.Agents.Orchestration.INotification` grain interface is removed.

Channel-aware notification routing:

- Console output (default, always available)
- Webhook (configurable URL)
- Telegram (existing skeleton)
- DevUI push (via SignalR hub — the Notification agent receives `INotificationAgent` interface which is resolved by Orleans DI; it uses an injected `IHubContext<NotificationHub>` to push to connected SignalR clients)

Agents don't choose the channel. They send `NotificationRequest` to `INotificationAgent`. The notification agent routes based on user preferences stored in `UserMemory`.

## 12. Breaking Changes from v0.1.0

| Change | Migration |
|--------|-----------|
| Agent constructor simplified (5 params -> 3) | Remove `history` and `trackingItems` from derived agent constructors. Agent base manages them internally. |
| `PublishAsync(name, payload)` removed | Use `PublishToStream(new MyTypedEvent(...))` or `PublishToTaskStream(taskId, evt)` |
| `HandleEvent(AgentEvent)` removed from IAgent | Implement `IStreamConsumer<TEvent>` instead |
| `AgentEvent` no longer public constructable | Use typed event records implementing `IEvent` |
| `INotification` grain interface renamed to `INotificationAgent` | Update all references from `INotification` to `INotificationAgent` |
| `IKnowledge` / KnowledgeAgent deprecated | Replaced by `IProjectMemory` / `ICodeMemory`. KnowledgeAgent remains in codebase for backward compatibility but is no longer part of the default agent team. Will be removed in v0.3.0. |
| `ScriptGenerator` output format changed | Generated scripts now use typed interfaces (`IRoslyn`, `IDotNet`) instead of `IAgent`. Method names updated to match current IAgent (`GetResponse` not `SendMessageAsync`). |

### Grain State Versioning

v0.2.0 changes the Agent constructor and adds new durable stores to derived types. For users running with persistent storage (CosmosDB):
- Existing grain state from v0.1.0 is forward-compatible — Orleans deserializes only the fields it finds
- New `[Memory]` stores (e.g., `orchestration-steps`) are created empty on first access
- The `[GrainType("agent-v3")]` remains unchanged — no grain type migration needed
