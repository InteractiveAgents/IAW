Communication Patterns

Not one pattern fits all — each has its place. The key is knowing when to use which.

📋 Shared Ledger (Pull)

Durable per-task event log. Agents append short structured events (~50 tokens). Other agents read the log as context when activated.

✅ USE FOR: Multi-agent task coordination, providing collaborative context, progress tracking, audit trail
❌ AVOID FOR: Real-time reactions, urgent notifications, UI updates
  • Zero LLM overhead for publishing
  • Zero LLM overhead for reading (injected as prompt context)
  • Durable — survives crashes
  • Agents don't need to be active to contribute

📡 Task Stream (Push)

Orleans stream per task. Agents subscribe to tasks they're working on. Events flow in real-time for monitoring and reactive agents.

✅ USE FOR: Validator monitoring, orchestration progress, step completion signals, approval gates
❌ AVOID FOR: Routine progress (use ledger), broadcasting to unknown consumers
  • Real-time — Validator can catch drift immediately
  • Targeted — only subscribed agents receive
  • Supports backpressure and sequencing
  • The "nervous system" of a running task

📢 Broadcast Channel (Fan-out)

Orleans BroadcastChannel with [ImplicitChannelSubscription]. All grains of a type receive the message. Fire-and-forget.

✅ USE FOR: UI updates (Telegram, DevUI, Dashboard), system-wide notifications, task completion announcements
❌ AVOID FOR: Agent-to-agent collaboration, anything requiring acknowledgment, LLM-heavy reactions
  • Decoupled — sender doesn't know receivers
  • Perfect for UI agents that display results
  • No LLM cost — UI agents just format and render
  • Not persistent — for notifications, not state

🔀 Smart Router (Rule-Based Push)

Non-LLM grain that pattern-matches critical events and routes to specific agents. Zero token cost.

✅ USE FOR: Build failures → fix agent, test failures → diagnostic agent, health alerts → incident response
❌ AVOID FOR: Ambiguous situations, creative decisions, anything requiring judgment
  • Zero LLM calls — pure pattern matching
  • Sub-millisecond routing
  • Handles critical events that need immediate action
  • Routing table is declarative and testable

📝 Team Lead Digest (Batched)

ThreadAgent periodically reads the ledger, summarizes with a cheap LLM (Haiku), and decides next actions. Compresses N events into 1 decision.

✅ USE FOR: Long-running tasks, multi-project coordination, periodic user updates, deciding "what's next"
❌ AVOID FOR: Time-critical events, simple linear workflows
  • 1 cheap LLM call per batch instead of N expensive ones
  • Provides human-readable progress summaries
  • Natural decision point for orchestration
  • ThreadAgent already has this role conceptually

🔗 Direct P2P (Existing)

Direct grain-to-grain calls via IAgent.GetResponse() or IReceiver<T>. Synchronous, full context transfer.

✅ USE FOR: Simple 1:1 delegation, tool-like operations (FileSystem.ReadFile), stateless queries
❌ AVOID FOR: Multi-agent collaboration, anything where context would be copied repeatedly
  • Simplest pattern — already works today
  • Fine for "command" operations (read file, run build)
  • Expensive for "conversation" operations
  • Keep for simple tool-like calls

Architecture Options

Three implementation approaches — from minimal to comprehensive

Option A: Layered Event Bus

Minimal viable architecture — 3 layers

Layer 1: Task Ledger

IDurableList<TaskEvent> per task grain. Append-only. Injected as context when agents are activated.

  • New: ITaskLedger grain
  • Events are structured records
  • ~50 tokens per event
  • Read by orchestrator before each agent call

Layer 2: Broadcast

BroadcastChannel for UI notifications. TelegramUI and DevUI subscribe implicitly.

  • AddBroadcastChannel("ui-notifications")
  • [ImplicitChannelSubscription] on UI agents
  • Fire-and-forget, no persistence needed
  • Replaces current ad-hoc event publishing

Layer 3: Critical Router

Non-LLM grain with routing table. Only handles failures and blockers.

  • New: IEventRouter grain
  • Pattern-match on event type + severity
  • Routes to pre-configured handlers
  • Zero LLM cost
Effort: Medium. ~2 weeks. Core changes: new ITaskLedger grain, BroadcastChannel config, Router grain, context injection in Agent base class.
Risk: Low. Additive — doesn't break existing patterns.
Token savings: ~50-60% on multi-agent tasks.

Option B: Full Event-Driven with Quality Gate

Comprehensive — adds Validator agent and Task Stream monitoring

Everything from Option A, plus:

  • Validator Agent — subscribes to task streams, monitors for hallucinations, drift, and errors. Uses cheap model (Haiku) for validation checks.
  • Task Stream (Orleans Streams) — real-time event flow per task. Validator and UI agents subscribe.
  • Team Lead Digest — ThreadAgent periodically reads ledger, produces summaries for long tasks.
  • Approval Gates — orchestration pauses at defined checkpoints, sends approval via broadcast to Telegram.

New Core Components:

  • ITaskLedger — durable event log grain
  • IEventRouter — rule-based routing grain
  • IValidator — quality gate agent
  • TaskStreamProvider — persistent streams per task
  • BroadcastChannel("ui") — UI notification bus
  • ApprovalGate — pause/resume pattern
  • History durability fix in DurableChatHistoryProvider
Effort: High. ~4-5 weeks. Significant core changes + new agent.
Risk: Medium. Validator agent needs careful prompt engineering.
Token savings: ~70-80% on multi-agent tasks. Plus catches errors early = fewer retries.

Option C: Adaptive Intelligence Platform

The full vision — self-optimizing event architecture

Everything from Option B, plus:

  • Adaptive Routing — Router learns from past task outcomes. If Excel agent frequently fails on chart generation, route chart tasks to a different agent.
  • Token Budget Manager — pre-allocates token budget per task based on complexity estimate. Agents get token allowances.
  • Replay & Recovery — if a task fails mid-way, the ledger serves as a checkpoint. Replay from last successful event.
  • Cross-Task Learning — Episode memory stores successful event patterns. Future similar tasks reuse proven flows.

Additional Components:

  • ITokenBudgetManager — grain-level token accounting
  • IAdaptiveRouter — ML-enhanced routing (uses past outcomes)
  • IReplayEngine — checkpoint + replay from ledger
  • Persistent Orleans Streams (Azure Event Hubs or equivalent)
  • Event schema registry with versioning
  • Full OpenTelemetry integration for event tracing
Effort: Very high. ~8-10 weeks. Deep architectural changes.
Risk: High. Complex, needs careful incremental delivery.
Token savings: ~85-90% + self-improving over time.

Recommendation

Start with Option B, designed to evolve into Option C.

Option A is too minimal — without the Validator, you have no quality gate and agents can hallucinate unchecked. Option C is the goal but too much for one release. Option B gives you the full event-driven architecture with quality assurance, and the Ledger + Stream foundation makes Option C features additive.

Token Usage Analysis

Quantifying the waste and the savings

Current Token Waste Patterns

1
Context Forwarding
When Thread forwards Agent A's full response to Agent B, it includes the entire conversation. A 5-step task copies context 5 times. By step 5, the prompt includes ALL previous outputs.

Cost: ~5,000-20,000 tokens per handoff
2
Redundant Discovery
Each agent re-discovers project context. Roslyn analyzes the workspace. DotNet discovers the solution. FileSystem lists files. They all do this independently.

Cost: ~2,000-5,000 tokens per agent per task
3
Failed Retries
When a build fails, the error + full context is sent to an LLM to decide what to do. Often the fix is mechanical (missing import, typo). A rule-based router could handle this for zero tokens.

Cost: ~3,000-8,000 tokens per retry cycle
4
Unused Agent Activation
CodeOrchestrator generates C# code that calls agents. If it calls 5 agents and 2 aren't needed, those agents still activate, load context, and produce "nothing to do" responses.

Cost: ~1,000-3,000 tokens per unnecessary activation

Issues & Current Gaps

What needs to be fixed before building on top

Critical Bugs

🔴
Conversation History Not Durable
CRITICAL — data loss risk
StoreChatHistoryAsync() adds messages to IDurableList but never calls WriteStateAsync(). Messages are only persisted when the full conversation turn completes. If the grain deactivates during an LLM call (10-30s window), all messages from that turn are lost.

Fix: Pass a persistence callback to DurableChatHistoryProvider. Call WriteStateAsync() after each history.Add().
Also: Make HistorySummarizer._lastSummary durable (store in state dict).
🔴
Memory-Only Stream Provider
All events lost on silo restart
Streams use .WithMemoryStreaming() — events exist only in RAM. On silo restart, all subscriptions and in-flight events vanish. Fine for dev, broken for production.

Fix: Configure persistent stream provider (Azure Event Hubs, or at minimum queue-based).

Architecture Gaps

🟡
No Shared Task Context
Agents working on the same task have no shared awareness. Each gets context forwarded by the orchestrator, duplicating tokens. Need: Task Ledger grain with shared event log.
🟡
No Broadcast Channels
UI updates (Telegram, DevUI) use ad-hoc stream publishing. No [ImplicitChannelSubscription]. Adding a new UI surface requires code changes in every agent that publishes notifications.
🟡
No Quality Gate
No Validator agent monitors task output. Agents can hallucinate file paths, produce incorrect calculations, or generate code that doesn't match requirements. Nobody checks.
🟡
No Event Schema
Event names are scattered hardcoded strings ("build.failed", "file.written"). No centralized schema. No type safety. Adding new events is error-prone.
🟡
Only 1 Stream Consumer
Out of 34 agents, only RoslynAgent consumes streams. 11 agents publish events that nobody listens to. The streaming infrastructure exists but is barely used.
🟡
No Smart Routing
All routing goes through LLM (AgentSelector). Mechanical decisions like "build failed → call DotNet" waste tokens on an LLM call. Need a non-LLM router for deterministic cases.
