The Three Pillars

1. Every Agent Is a True Expert
Not "an LLM that knows about Git." A Git expert with real tools.
  • SDK-backed tools — Excel agent uses OpenXML SDK, not LLM hallucinating formulas
  • Expert prompts — Each agent's system prompt is curated expertise, not generic instructions
  • Domain knowledge — Roslyn agent knows the syntax tree API. It doesn't guess — it navigates the actual AST.
  • Bounded responsibility — Each agent knows exactly what it can and cannot do. It delegates what it can't.
2. Memory Makes It Personal
"Why did you do it this way?" — "Because 2 months ago you said..."
  • Episodic memory — Remembers past conversations, decisions, outcomes
  • User preferences — Coding style, communication preferences, timezone, tool preferences
  • Explainability — Can trace any decision back to the memory/preference that drove it
  • Long-term learning — Gets better at predicting what you want over time
3. Domains Collaborate, Not Compete
Your finance report uses the coding agent to fetch data AND the Excel agent to format it.
  • Cross-domain orchestration — "Analyze my expenses" touches Data, Documents, and Personal Assistant domains
  • Shared Ledger — All agents on a task share context without duplicating tokens
  • Quality gates — Validator ensures cross-domain output is consistent
  • Event-driven, not chain-driven — Agents publish progress, not forward context

Agent Expertise Design

What makes an IAW agent a TRUE expert vs. "an LLM with a role string"

Expert Agent Anatomy
EXPERT AGENT = SDK Tools + Domain Prompt + Bounded Responsibility + Learning

 1. SDK-Backed Tools (the hands)
    - NOT: LLM generates code/text that represents the output
    - YES: LLM decides WHAT to do, SDK tools EXECUTE it precisely
    - Example: Excel agent calls SetFormula("B2", "=SUM(B3:B50)")
    - Example: Roslyn agent calls workspace.GetSymbol("MyClass")
    - The LLM is the brain, the SDK is the hands

 2. Expert System Prompt (the knowledge)
    - NOT: "You are an Excel assistant"
    - YES: "You are an Excel expert. You understand:
            - Cell references (A1, $A$1, A1:B10)
            - Formula functions (VLOOKUP, INDEX/MATCH, SUMIFS)
            - Chart types and when to use each
            - Pivot table design principles
            - Conditional formatting patterns
            - Data validation rules
            You ALWAYS use tools to execute — never generate raw XML."
    - The prompt encodes REAL expertise, not just a role

 3. Bounded Responsibility (the scope)
    - Each agent knows exactly what it CAN and CANNOT do
    - When asked something outside scope: delegates, doesn't hallucinate
    - Git agent doesn't try to fix code. It reports the diff and delegates to Roslyn.
    - Excel agent doesn't analyze data. It formats what Finance agent computed.

 4. Context Injection (the memory)
    - PreferenceAgent injects user-specific rules
    - KnowledgeAgent injects project conventions
    - EpisodeMemory injects relevant past experiences
    - All injected as structured context, not "remembered" by the LLM

Memory & Explainability Architecture

How IAW remembers, learns, and explains its decisions

Memory Layers

Layer 1: Working Memory
Current conversation + task ledger. Exists during task execution.

Conversation history (IDurableList<ChatMessage>) + current task's shared ledger. Lost when conversation ends (but stored to episodic memory).

Layer 2: Episodic Memory
Past conversations, task outcomes, decisions made. Searchable via vector DB.

Every completed task → episode stored in Qdrant. Includes: what was asked, what happened, what was decided, what worked/failed. This is how IAW can say "remember when we..."

Layer 3: Semantic Memory
Learned facts, patterns, conventions. The knowledge base.

KnowledgeAgent: architecture decisions, patterns, conventions. PatternMemory: proven code patterns. CodeMemory: codebase structure. UserMemory: personal facts.

Layer 4: Behavioral Rules
Preferences that modify how agents work. The personality layer.

PreferenceAgent: "don't mock DBs", "use Cosmos for low latency", "prefer Opus for architecture decisions". Injected as context when relevant agents activate.

Self-Improvement Domain

IAW improving itself — safely, incrementally, with human approval gates

Self-Improvement Loop
DETECT → ANALYZE → GUARD → IMPLEMENT → DEPLOY → MONITOR

1. DETECT (PerformanceMonitor)
   - Scheduled health checks on all agents
   - Token usage anomalies (agent X using 3x expected)
   - Error rate spikes (agent Y failing 30%)
   - Latency patterns (response time degradation)

2. ANALYZE (ChangeAnalyzer)
   - Root cause analysis using traces + logs
   - Proposes specific code changes
   - Estimates impact and risk level

3. GUARD (ArchitectureGuard)
   - Reviews change against recorded decisions
   - Checks: public contract changes?
   - Checks: cross-domain impact?
   - Checks: architectural alignment?
   - BLOCKS if change violates principles

4. IMPLEMENT (IAWSystem)
   - Applies code changes
   - Adds/updates tests
   - Builds and runs full test suite

5. DEPLOY (SafeDeployer)
   - HUMAN APPROVAL GATE (Telegram buttons)
   - Canary deploy (single silo)
   - Health check (5 min)
   - Full deploy if healthy
   - Auto-rollback if not

6. MONITOR (PerformanceMonitor)
   - Confirms improvement metric
   - Stores episode in memory
   - Loop back to DETECT

Key Safety Principles

  • Human always approves — the loop proposes, user decides. Uses DurableTaskCompletionSource (from Accede pattern) for crash-proof approval gates.
  • Architecture Guard is non-negotiable — every change reviewed against stored decisions. No "quick fix" that breaks a principle.
  • Tests must pass — no deploy without green tests. Self-improvement includes writing tests for the improvement.
  • Auto-rollback — if canary deploy shows degradation, rollback is automatic. No human intervention needed for safety.
  • Episode memory — every self-improvement cycle is recorded. The system learns what improvements work and what doesn't.

What's Missing

Gaps between today's IAW and the v0.0.3 vision

Critical (Must Fix Before Building On Top)

Conversation history not durable
StoreChatHistoryAsync() doesn't call WriteStateAsync(). Messages lost on grain deactivation. HistorySummarizer._lastSummary also not durable.
Memory-only stream provider
All events lost on silo restart. Need persistent or at least queue-backed provider.
No shared task context (Ledger)
Agents working on same task have zero shared awareness. Full context forwarded via Thread = token explosion.

High (Required for v0.0.3 Vision)

No PreferenceAgent
User corrections aren't stored as behavioral rules. No injection of preferences into other agents' context. IAW keeps repeating the same mistakes.
No ExplainabilityAgent
Can't trace decisions back to conversations/preferences. "Why did you do X?" gets a generic answer, not a traced one.
No Validator agent
No quality gate on multi-agent output. Hallucinations go unchecked. Numbers can be inconsistent across agents.
No Broadcast Channel
UI updates use ad-hoc publishing. Adding new UI surface requires changes in every publishing agent.
No Smart Event Router
All routing through LLM. Mechanical decisions (build failed → fix) waste tokens on AgentSelector.
No Human-in-the-Loop approval gates
No DurableTaskCompletionSource pattern. Can't pause orchestration, wait for Telegram approval, and resume. Accede has this — IAW doesn't.
No domain organization
All agents flat in src/Agents/. No domain boundaries. No domain-specific context injection.
Event schema is scattered strings
Event names hardcoded as strings. No type safety. No discoverability. Need typed event hierarchy.

Medium (Important for Full Vision)

No Documents domain
No Excel, Word, PDF, or Vision agents. Need OpenXML SDK integration for real document generation.
No Data domain
No Finance, Analytics, or WebResearch agents.
No Self-Improvement domain
No ArchitectureGuard, SafeDeployer, PerformanceMonitor, ChangeAnalyzer.
Git agent is basic
Only status/commit/diff/log/revert. Missing: rebase, cherry-pick, bisect, stash, conflict resolution, worktree.
No cron scheduling
DurableJobs support interval-based only. Need cron expressions for "every Friday at 5 PM CET" with DST handling.
No Team Lead digest pattern
Long-running tasks have no periodic progress summaries. User gets nothing until task completes.
Core lib test coverage is thin
Event system, streams, scheduling, history — all need thorough unit and integration tests.

Lessons from AccedeConciergeFork

Patterns to adopt, adapt, or skip

Adopt: DurableTaskCompletionSource
Grain-based promise for human-in-the-loop
  • Orchestration calls RequestApproval() → blocks on grain
  • Telegram sends approval buttons
  • User clicks → TrySetResult() → orchestration resumes
  • Survives silo restarts — state is journaled
  • IAW use: Self-improvement approval, risky operation confirmation, multi-step wizard
Adopt: Typed ChatItem Hierarchy
Polymorphic messages enable rich UI
  • Not just "text messages" — typed items: UserMessage, AssistantResponse, PreferenceUpdated, TripRequestDecision
  • Each type has IsUserVisible flag — control what reaches UI
  • Each type can override ToChatMessage() — different representation for LLM vs user
  • IAW use: ApprovalRequest, ProgressUpdate, FileAttachment, ValidationResult, LedgerEvent
Adopt: IDurableQueue for Message Ordering
Better concurrency than inline processing
  • Accede uses IDurableQueue<ChatItem> + AsyncManualResetEvent
  • Messages queued durably, processed in order
  • Background pump loop handles one at a time
  • IAW use: Agent message inbox — prevents race conditions, enables cancellation
Adapt: Side Conversation Pattern
Agent-to-agent chat for complex negotiation
  • Accede: Liaison manually orchestrates chat with TravelAgent in a loop
  • IAW adaptation: Formalize as SideConversation(IAgent target, string goal) in Core
  • Useful for: AgentSelector ↔ candidate agents, Validator ↔ questioned agent
Skip: Custom Async Method Builder
Too complex for current needs
  • Accede's DurableTask<T> with custom async builder is impressive but over-engineered for IAW
  • IAW already has DurableJobs for scheduling and grain state for persistence
  • Revisit only if we need deterministic replay (Option C from previous review)
Skip: SSE Chat Streaming API
IAW uses different client patterns
  • Accede streams via SSE to React frontend
  • IAW uses: Telegram webhooks, Blazor SignalR, MCP protocol
  • No need for SSE unless adding a standalone web client
